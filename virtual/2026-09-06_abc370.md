## Dの振り返り

**解説の型**:
二分探索 + 削除可能なソート済み集合（またはUnion-Findで「次に生きている要素」を管理）

**自分の方針**:
1. 愚直実装 → TLE
2. 行ごと・列ごとに生きている壁を持ち、二分探索で直前・直後を取る → 実装が間に合わず

**なぜ当てられなかったか**（1つ選ぶ）:

- [ ] 型を知らなかった
- [ ] 型は知っているが、問題文から結びつかなかった
- [x] 型は当たったが実装できなかった
- [ ] 実装したがTLE
- [ ] 時間が足りなかった

**自分の解法の計算量**: 愚直は最悪 O(Q(H+W))。H×W ≤ 4×10^5、Q ≤ 2×10^5 なので桁が足りない（Rubyの定数倍以前の問題）

**想定解の計算量**: O((HW + Q) log) 程度。削除可能なソート済み集合が要る

**差がどこで生まれたか**:
方針は正解だった（rows/cols に昇順で持つ、bisect_left = bsearch_index）。
崩れたのは実装の2点のみ:
1. 壁がある/ないの判定を行と列で2回走らせた → 外に出して1回にする
2. 見つけながら壊した → walls 配列に集めてから一括で削除
境界は `j < size` と `j-1 >= 0` の2条件で済む。nil/0 の3分岐は不要だった。

**Ruby特有**: 削除可能なソート済み集合が標準にない。
sorted_containers gem の SortedArray で解決できる
または「次に生きている要素」を指す Union-Find（4方向ぶん）。

**詰まった具体的な箇所**:
bsearch_index を単調でない配列に適用しようとした（本番中）。
→ 二分探索は「探す対象を単調な列に作り替える」ところまでがセット。
行・列を独立に扱う設計で、分岐が5重になり見通しを失った。

**次の一手の候補**（未検証）:
- - 配列 + `bsearch_index` + `delete_at`（delete_at は O(N)。SortedArray は内部で分割して持つので1回の移動量が小さいはず。要実測）
- 「次に生きている要素」を指すUnion-Find（4方向ぶん必要）
- 遅延削除（消したことを記録し、探索時にスキップ）

鍵になる性質: **壁は減る一方で、増えない**

**次に同じサインを見たら**:
- 「グリッドの各方向で最初に○○を探す」→ 行ごと・列ごとに生きている要素を昇順で持つ
- 二分探索を使うと決めたら、探す配列が単調か先に確認する
- 複数箇所を消すときは、全部見つけてから一括で消す（見つけながら消すと状態がずれる）

## 愚直解（TLE）

```ruby
h, w, q = gets.split.map(&:to_i)
g = Array.new(h) { Array.new(w, 1) }

di = [-1, 1, 0, 0]
dj = [0, 0, -1, 1]

q.times do
  i, j = gets.split.map { it.to_i - 1 }
  if g[i][j] == 1
    next g[i][j] = 0
  end

  4.times do |k|
    ni, nj = i, j
    loop do
      ni += di[k]
      nj += dj[k]
      break if ni < 0 || nj < 0 || ni >= h || nj >= w
      break g[ni][nj] = 0 if g[ni][nj] == 1
    end
  end
end

puts g.sum(&:sum)
```
